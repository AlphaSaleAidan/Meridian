## P1 — High

### P1-1. Phone agent confirms FAILED orders to the caller (ignores `order_result.success`)
- **File:** `src/api/routes/phone.py:1001-1036` (`submit_order` handler)
- **Detail:** After `order_result = await _dispatch_order(...)`, the code does
  `order_id = order_result.order_id or f"MRD-{abs(hash(call_sid)) % 9000 + 1000}"` and then proceeds straight to the customer confirmation ("Great! I've placed your order... Your order number is {order_id}"). **It never checks `order_result.success`.** `grep` for `.success` in `phone.py` returns nothing.
- **Consequence:** When `create_pos_order` returns `success=False` (unknown POS system, missing/!authenticated connection config, Square missing `location_id`), the caller is still told the order was placed and is given a *fabricated* `MRD-####` number derived from `hash(call_sid)`. The order never reaches the kitchen. For a live food-ordering line this is silent revenue/trust loss.
- **Repro:** call `submit_order` for a session whose POS resolves but has no usable config → `_dispatch_order` returns `OrderResult(success=False, order_id="")` → caller hears a confirmation with a made-up number.
- **Fix:** branch on `order_result.success` (and `fallback_used`). On failure/queued-only, tell the caller the order could not be confirmed or transfer to a human; do not emit a fake order number as if accepted.

### P1-2. Order-dispatcher "queued" fallback silently drops the order but reports success
- **File:** `src/services/pos_connectors/order_dispatcher.py:86-99` (`_fallback_order`)
- **Detail:** Fallback chain is API → SMS → Email → "queue". If the merchant has no `merchant_phone`/`merchant_email`, or both `_send_sms` and `_send_email` fail, it sets `sent_via = "queued"`, logs `"Order {id} queued for manual processing"`, and returns `OrderResult(success=True, ...)`. **There is no actual queue** — "queued" is only a log line; nothing is persisted and the merchant is never notified.
- **Consequence:** combined with P1-1, a real order can vanish entirely while the caller believes it is confirmed and `success=True` propagates upward.
- **Repro:** dispatch an order for a CSV-only / unknown POS with no merchant contact on the session → returns `success=True`, `fallback_reason="Sent via queued (no direct API)"`, order persisted nowhere.
- **Fix:** the "queued" branch must persist the order (DB row / dead-letter table / alert) or return `success=False`. Don't return success for an order nobody received.

### P1-3. Toast webhook processed WITHOUT signature verification (spoofable)
- **File:** `src/api/routes/webhooks.py:359-385`
- **Detail:** The handler fails closed if `TOAST_WEBHOOK_SECRET` is unset (returns 503), but when the secret *is* set it logs `"Toast webhook accepted WITHOUT signature verification — helper pending in src/toast/"` and processes the payload anyway via `background_tasks.add_task(_process_toast_webhook, ...)`. A `TODO(follow-up)` marks the missing HMAC check.
- **Consequence:** anyone who can reach the endpoint can POST forged Toast events (`eventType`, `restaurantGuid`) and have them processed. Webhook-spoofing / data-poisoning risk on a public endpoint.
- **Fix:** implement the HMAC signature verification against `TOAST_WEBHOOK_SECRET` before enqueueing; reject mismatches with 401.

## P2 — Medium

### P2-1. Clover incremental sync: a single `get_merchant()` failure aborts the ENTIRE sync
- **File:** `src/clover/sync_engine.py:310` (inside `run_incremental_sync`)
- **Detail:** `get_merchant()` is called only to pin the currency on the mapper. It is *not* wrapped, unlike the adjacent `_fetch_config_lookups` (order-types/tenders) which are explicitly "non-fatal" (sync_engine.py:77/84) and the product-lookup load which is try/except'd. The whole method is wrapped in one big `try/except Exception` (sync_engine.py:354-360) that logs `"Incremental sync failed"`, appends to `result.errors`, sets progress `"error"`, and returns an empty result.
- **Consequence:** if Clover's merchant endpoint is flaky/rate-limited/permission-scoped while the orders endpoint is fine, the incremental sync produces **zero transactions** purely because it couldn't fetch a currency code. Inconsistent error-handling posture vs. the other lookups.
- **Fix:** wrap `get_merchant()` non-fatally (default currency to None / last-known) like the other config lookups; let order sync proceed.

### P2-2. Stale test fixture breaks 2 tests (code/test drift on `get_merchant`)
- **File:** `tests/api/test_pos_digest_flow.py:58, 78` — `test_clover_incremental_loads_product_lookup`, `test_clover_incremental_without_db_is_safe`
- **Detail:** Both fail with `KeyError: 'lookup'` because the test's `_FakeOrdersClient` does not implement `get_merchant()` (added later to `run_incremental_sync`). The unhandled `AttributeError` is swallowed by the broad except (see P2-1), so the `FakeMapper` that records `captured["lookup"]` is never constructed.
- **Repro:** `python3 -m pytest tests/api/test_pos_digest_flow.py` → 2 failed, 36 passed.
- **Fix:** add `get_merchant`/`list_order_types`/`list_tenders` to `_FakeOrdersClient` (and ideally fix P2-1 so the fatal call becomes non-fatal).

### P2-3. Order-dependent / flaky test
- **File:** `tests/swarm_eval/test_agent_registry.py:33` — `test_registry_passes_validator`
- **Detail:** **Passes in isolation** (`pytest tests/swarm_eval/test_agent_registry.py` → 5 passed) but **failed in the full-suite run** (`AssertionError` from `validate_agents.validate()`). Full-suite failure count varied between runs (7 vs 8), confirming non-determinism — a sibling test mutates global state (cwd / env / a module-level cache / the registry file) that `validate_agents.validate()` depends on.
- **Fix:** isolate `validate_agents` global state (cwd-independent path resolution, reset caches via fixture); identify the polluting test.

### P2-4. SMS stub returns HTTP 200 with an error body, contradicting its own contract
- **File:** `src/api/routes/sms.py:22-31`
- **Detail:** When the phone-agent sidecar (`services/phone_agent/sms_order.py`) is importable, the real router mounts (confirmed live: `/sms/inbound` → 405 on GET = exists). When it is NOT importable, the fallback `_sms_stub` `@router.post("/inbound")` returns `{"error": "sms_handler_not_available"}` with an implicit **200**. The module docstring claims the unwired case "will 404, which is the correct signal" — but a 200 makes Twilio treat the inbound SMS as successfully handled and drop it silently.
- **Fix:** the stub should return an explicit `404`/`503` so a misconfigured deploy is detectable, matching the documented intent. (Not active in prod — sidecar is present — but a latent foot-gun for new deploys.)
