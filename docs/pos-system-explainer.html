Meridian · POS Read-Only System

Connect → Digest → Propagate

How a merchant's point-of-sale data flows into Meridian, read-only, and what we hardened across the rebuild. Three stages, one job: read the merchant's sales without ever writing back to their POS.

Stage 1
Connect POS
Square / Clover OAuth or a manual key paste → one stored connection.
Stage 2
Digest (read-only)
Pull orders, items, payments, refunds → normalize to our schema.
Stage 3
Propagate
Land it in the DB so the dashboard sees it — without clobbering rows.

Use ← / → to move through the stages and the upgrades behind each.

Stage 1

Connect POS — three doors, one connection

Square / Clover OAuthor Manual key pasteor CSV upload→ pos_connections row→ background backfill

Every path lands in one pos_connections record (encrypted token) and opens the dashboard gate. OAuth uses an HMAC-signed state token (CSRF) with a 10-minute TTL.

What we hardened

  • Tenancy guard: /connect & /disconnect now require a JWT + org membership on the body org_id — closes a cross-tenant write gap.
  • Env-aware Square: test & connect route through the Square client, honoring sandbox vs production (was hardcoded to prod).
  • Clean disconnect: tears down both gate fields and clears the stored token (no half-open dashboard, no token left at rest).

Stage 2 · read-only

Digest — how we read the merchant's data

merchant + locations→ categories + items→ orders (18 mo, chunked)→ payments + refunds→ inventory

A backfill pulls history once; an incremental sync + webhooks keep it current. Provider-specific mappers normalize everything into our shared schema (cents, ISO timestamps, products / transactions / line items).

Read-only means read-only: we fetch and map. We never push anything back to Square or Clover.

Stage 2 · upgrades

Digest — data we were silently losing

● before   ● now

  • Incremental items had no product link — every recent line item stored product_id = NULL (the lookup wasn't loaded). Now loaded from the DB for both providers.
  • Split payments collapsed to one tender — cash+card recorded only the first. Now every tender captured (Clover + Square).
  • Refunds ignored — a refunded order kept its gross total, overstating revenue. Now Square refunded_money + Clover /refunds folded in.
  • Clover service charges invisible — auto-gratuity/fees weren't fetched. Now captured.
  • Multi-register blind — the device that rang an order was dropped. Now captured for attribution.

Stage 3

Propagate — landing it without overwrites

products→ transactions→ transaction_items→ dashboard reads

Writes go in FK-safe order through one shared write path. The dashboard then reads transactions, revenue, products, insights from these tables.

The old hazard

Every row id was random (uuid4). Re-syncs duplicated line items, churned transaction PKs (orphaning items), and the webhook path keyed on a column line items didn't have → clobbered each other.

The fix

Deterministic uuid5 ids from each row's natural key + provider. Re-syncs upsert the same row; distinct rows never share an id; one unified conflict key everywhere.

Stage 3 · invariants

Why rows can't write over each other

  • Deterministic ids: uuid5(org, provider, natural_key) → idempotent re-syncs, stable foreign keys.
  • Stable line-item identity: each item carries {txn_id}:{line_id} so distinct lines never collide.
  • One conflict key: all transaction_items writes upsert on (id, transaction_at) — backfill, incremental, and webhook agree.
  • Provider in the key: a Clover and a Square order with the same external id can't collide.
  • Self-healing writes: a partial failure converges on the next sync (idempotent). Optional single-transaction RPC is wired behind a flag.

Status & what's next

Where this lives

All three stages are built, tested, and documented on branch feat/core-flows (off main) — 34 passing tests, nothing deployed yet.

  • Safe to merge independently: every upgrade writes into existing columns (the metadata JSONB), never a new column — so no migration is required to ship.
  • One coordinated migration, later: promote the metadata.* fields (tenders, refund_cents, service_charge_cents, device_id) to queryable columns, enable the atomic-write RPC, and flip on per-provider tables.
